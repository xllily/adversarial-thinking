# Change Decisions

Use within the current mode when a consequential route choice has unresolved
assumptions that could change the next commitment. This is a reference, not a
fifth mode, permission grant, mandatory report, or scoring gate.

## Frame: recover the real baseline

- Identify the outcome, acceptance conditions, current phase, evidence and
  authority. Distinguish accepted decisions and real external constraints from
  the present implementation and the model's own provisional choices.
- Existing work may provide reusable output and verification evidence. Historical
  effort is sunk; future revalidation, relearning, migration and handoff are not.
  Even an implementation without a formal decision record may already have users.
- Identify which contracts, data boundaries, operating entrypoints, responsibilities
  or approved budgets would actually change. Consider cumulative task impact,
  not only the latest patch. File count and code size are signals, not authority.

## Countermodel: compare keeping and changing fairly

Challenge the assumption most likely to change the decision. Compare the proposed
change with a sufficient correction of the current route, or challenge continued
patching when evidence favors a different route. Do not manufacture alternatives
or require proof that a local fix is impossible before considering refactoring.

Use the same goals, constraints and observation horizon for both. Aesthetic
preference does not establish a benefit; familiarity does not establish that the
old route is best. Include a transition only when it adds value, with its own
compatibility and eventual removal costs.

In Brainstorm, preserve unscored divergence before convergence. Do not use this
reference to suppress ideas before there is a proposed commitment.

## Discriminate: count future costs and resolve the decisive unknown

Compare implementation and tool costs, review and regression work, migration,
recovery, relearning or reconfiguration, handoffs and waiting, and maintenance
within the relevant horizon. A solo user's future work matters too. Separate
person-hours, money and elapsed time unless a conversion is justified; avoid
counting the same cost twice.

Use observed frequency, explicit plans and ranges for future benefits. Mark
unknowns rather than inventing probabilities or self-confidence scores. Optional
weights express stakeholder preferences, not permission or objective certainty.
Check whether reasonable changes in the estimates reverse the choice. Run the
cheapest authorized check that can distinguish the routes; stop once evidence
is sufficient. No fixed ROI, diff budget, or exhaustive cost worksheet is required.

## Integrate: assess deeply when needed, ask only for new authority

Assessment depth and approval are separate. Within already authorized discretion,
choose the sufficient route, implement and verify it through the host workflow,
including substantial refactoring when warranted. Do not turn a high-impact but
authorized task into repeated approval requests.

If the actual choice crosses an uncovered boundary, prepare the specific evidence,
alternative, affected work and recovery conditions; seek only the missing decision.
Continue safe authorized work that does not depend on it. Respect review-only scope.
Tool access, a successful test or another agent's recommendation does not expand
authority. Reuse relevant decisions and approvals already present in the task.

Do not retain an unsafe or ineffective route merely because change was declined;
state the unresolved constraint and offer a bounded check, authorized mitigation,
deferral or a decision about the goal. Do not silently weaken acceptance criteria.

Record only what the existing task, PR or decision log lacks: what changed, why,
the affected boundary, authority source, verification and recovery. Return to
execution or the mode's native result. Reopen only for new material evidence,
a failed prediction, or a real change in boundary.
